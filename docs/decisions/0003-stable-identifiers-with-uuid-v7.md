# ADR 0003 — Stable identifiers with UUID v7

## Status

Accepted

## Date

2026-08-07

## Context

devGarden must create durable domain objects while offline on Windows and, later, Android and other devices. Those objects need identities that survive persistence, database movement or reconstruction, import and export, renaming, hierarchy changes, and future synchronization. Creating an Idea must never require a server or central identifier allocator.

Persisted objects requiring durable identity include Workspaces, Projects, Apps, Idea Groups, Ideas, Documents, Content Blocks, Flowcharts, Flowchart Nodes, Flowchart Connections, Snippets, Tasks, Tags, Relationships, and other future sync-capable domain records.

[ADR 0002](0002-local-persistence-with-drift.md) selected Drift over SQLite but intentionally left stable identifier format unresolved.

## Decision

devGarden will use **UUID version 7** as the stable identifier format for persisted domain objects that require durable identity.

UUID v7 identifiers are generated by the application without a server. A newly created offline object can receive its final stable identity before persistence. Repository implementations persist that identity, and future synchronization must preserve it rather than replace it with a server-side or database-local value.

UUID v7 is selected because it provides globally unique offline identity with negligible collision risk, requires no central authority, uses a standard UUID representation understood across databases and developer tooling, and has timestamp-based ordering characteristics that can improve index locality compared with fully random UUID v4 values. It supports durable references between independently created objects and is suitable for future multi-device synchronization.

The exact Dart UUID v7 package or implementation is **TBD — requires architectural decision before implementation.** It must generate RFC-compatible UUID v7 values, support Windows and Android, remain practical for possible iOS, Linux, and macOS support, be actively maintained and testable, and avoid unnecessary dependencies.

## Identity versus ordering

UUID v7 is an identifier, not the primary user-controlled ordering mechanism. Explicit sort-order fields remain required for reorderable collections such as Workspaces, Projects, Apps, Idea Groups, Content Blocks, Tasks, Flowcharts, and other ordered content. User-controlled order must not be derived solely from UUID timestamp characteristics.

Created and updated timestamps remain explicit domain metadata. Information encoded in a UUID v7 value does not replace `created_at` or `updated_at`.

## Persistence considerations

SQLite with Drift remains the accepted persistence stack. UUID v7 is the stable domain identity regardless of database representation.

The SQLite representation is **TBD — SQLite representation of UUID v7 identifiers.** Canonical UUID text and a 16-byte binary representation are candidates, but this ADR does not select between SQLite `TEXT` and `BLOB`. Domain and application code must not depend on that storage choice.

SQLite row IDs or integer surrogate values may exist internally if later implementation evidence justifies them. They are not devGarden's canonical object identity, must not be exported as canonical IDs, must not be relied upon across devices, and must not be used as synchronization identity. Relationships conceptually reference stable domain UUIDs. A second public identity system requires a future ADR.

## Domain boundaries

- Stable IDs belong to domain identity.
- IDs are generated before persistence when necessary.
- Repository implementations persist IDs without redefining their meaning.
- Drift table classes and database-local details do not define object identity.
- UI widgets must not invent alternate identity schemes.
- Import and export should preserve IDs when representing the same logical object.
- Copying or duplicating an object normally creates a new UUID because it creates a new logical object.
- Moving an object between a Workspace, Project, App, or Idea Group does not change its ID.
- Renaming or editing an object does not change its ID.
- Synchronization preserves the original stable ID.

Object titles and filesystem-like paths are not canonical identity. UUID references remain durable when display names, grouping, tree position, or pinboard position change.

Stable UUID identities support relationships such as related Idea to Idea, Flowchart Node to Idea, Task to Idea, Document to App, Snippet to App, Tag Assignment to an object, Relationship source to target, and Document links to real devGarden objects.

## Offline implications

The capture-first path can open devGarden offline, create a new Idea, assign its final UUID v7 locally, accept writing immediately, save locally, close and reopen later, and eventually synchronize without identity replacement. Identifier generation must add no visible capture friction.

## Import and export implications

Future native devGarden export formats should preserve IDs when exporting the same logical objects. Import semantics remain **TBD — import identity and collision policy.** Restoring the same object may preserve identity, while creating a new copy may require a new UUID.

Human-oriented Markdown export does not necessarily need to expose internal identifiers visibly unless its eventual format requires them. This ADR does not define export formats.

## Synchronization implications

UUID v7 provides stable identity to a future synchronization system, but does not select a backend, cloud database, protocol, conflict algorithm, or authentication provider. Uploading an object must not replace its UUID. A server may use internal database IDs, but those values do not replace devGarden domain identity.

UUID v7 does not eliminate the need for synchronization metadata, explicit timestamps, ordering, versioning, or conflict handling.

## Security and privacy

UUIDs identify records but are not secrets or authentication tokens. Knowing an object UUID must never imply authorization, and future shared or cloud systems require independent access control.

UUID v7 timestamp characteristics may reveal approximate creation time when IDs are exposed. The privacy effect of external ID exposure must be considered when sharing or public-link features are designed.

## Alternatives considered

### UUID v7

**Advantages:** Globally unique offline generation, standard UUID format, time-ordered characteristics, good synchronization fit, better database and index locality than fully random identifiers, and no central allocator.

**Disadvantages:** Longer and less human-readable than integers, application-side generation, unresolved SQLite representation, and an unresolved Dart implementation or package.

**Decision:** Selected.

### UUID v4

**Advantages:** Extremely common, simple random generation, excellent collision resistance, broad ecosystem support, and offline generation.

**Disadvantages:** Fully random ordering, poorer index locality than time-ordered identifiers, and no time-ordering characteristic.

**Decision:** Not selected because UUID v7 provides the same core offline and global-identity benefits with useful time-ordering characteristics.

### ULID

**Advantages:** Globally unique, time-sortable, compact and more human-friendly in text, and available offline.

**Disadvantages:** Less universally standardized across developer systems than UUID and uses different ecosystem conventions.

**Decision:** Not selected because devGarden benefits from a standard UUID representation.

### SQLite auto-increment integer only

**Advantages:** Compact, simple, efficient for SQLite indexing, and easy to implement locally.

**Disadvantages:** Device-local identity, collisions when independent databases merge, identity remapping for synchronization and import, poor fit for multi-device offline creation, and database allocation becomes object identity.

**Decision:** Rejected as canonical identity.

### Internal integer plus public UUID

**Advantages:** Compact local foreign keys, stable external identity, and possible optimization for some database operations.

**Disadvantages:** Two IDs per object, more mapping and debugging complexity, more opportunities for bugs, and no current evidence that devGarden's expected scale requires it.

**Decision:** Not selected as the default architecture. Future profiling may justify internal surrogate keys without changing UUID domain identity, but that requires an explicit implementation decision.

## Consequences

### Positive

- Identity can be generated safely while offline.
- Independently created multi-device records are synchronization-ready.
- Relationships and links remain durable across moves and renames.
- UUIDs interoperate with standard databases, APIs, formats, languages, and tools.
- UUID v7 offers useful time-ordered characteristics.
- Domain identity is independent of SQLite row allocation.

### Negative and risks

- UUIDs are larger than integers and less convenient for humans to type or read.
- A Dart UUID v7 implementation or package still requires selection.
- SQLite text versus binary representation still requires selection.
- UUID v7 values encode timestamp information.
- Indexing and query performance still require careful implementation and measurement.

UUID v7 does not replace explicit timestamps, user-controlled ordering, synchronization metadata, or conflict resolution.

## Follow-up decisions

Implementation note (2026-08-07): The first persistence slice selected the Dart `uuid` package for RFC 9562 UUID v7 generation and canonical UUID strings stored as SQLite `TEXT`. IDs are generated application-side before repository insertion, while domain code uses an `EntityId` value object independent of SQLite representation. This note records the later implementation without rewriting the accepted decision. ## Principle alignment

- **Capture first:** final object identity is generated locally without delaying a new Idea or requiring metadata.
- **Local-first:** devices can create durable records independently while offline.
- **Everything must be easy to find:** durable references survive renaming, moves, and presentation changes.
- **Work with developer tools:** standard UUIDs interoperate broadly with databases, APIs, import/export formats, and developer tooling.
- **Shared content, separate presentation:** domain identity remains stable while platform-specific layouts change independently.
